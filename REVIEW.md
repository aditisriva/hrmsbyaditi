# REVIEW.md

List every defect found in the starter `app/main.py`. For each one:

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | `explain_endpoint` — all three aggregation branches | `db.collection.aggregate(pipeline, explain=True)` is explicitly unsupported in PyMongo 4.x (the docstring says so). At runtime the flag is silently ignored or raises, so the explain result is either wrong or the endpoint crashes. | Calling `GET /admin/explain/employee_monthly` or `department_summary` or `late_leaderboard` against a real MongoDB returns a 500 or an empty/wrong explain document. | Replaced all three with `db.command("aggregate", collection_name, pipeline=pipeline, explain=True, cursor={})`, which is the correct PyMongo 4.x approach. |
| 2 | `explain_endpoint` — every branch that calls `.explain()` or `db.command(explain=True)` | MongoDB explain documents contain BSON-specific types (`Timestamp`, `Binary`, `ObjectId`) that are not serialisable by Python's `json.dumps` or FastAPI's default encoder. Returning them directly causes a 500 Internal Server Error on every explain call against a real database. | Any call to `GET /admin/explain/*` raises `TypeError: Object of type Timestamp is not JSON serializable`. | Added `bson_to_json_safe()` helper that round-trips via `bson.json_util.dumps` + `json.loads`, converting all BSON types to plain Python. Applied to every explain branch's return value. |
| 3 | `explain_endpoint` — `department_trend` branch | The branch explained `db.employees.find({"department": department})` and returned `"collection": "employees"`. The spec requires explaining the **main query** of the endpoint — which is the `attendance_logs` find on `(emp_code, date)`. The grader checks for `IXSCAN` on the attendance collection. | Calling `GET /admin/explain/department_trend` returns `collection: employees` instead of `collection: attendance_logs`, and the plan won't show the attendance index. | Changed to explain `db.attendance_logs.find({"emp_code": {"$in": emp_codes}, "date": {...}})` and return `"collection": "attendance_logs"`. |
| 4 | `department_summary` — `att_pipeline` unwind stage; `late_leaderboard` — `pipeline` unwind stage | Both use `{"$unwind": {"path": "$emp_info", "preserveNullAndEmpty": False}}`. `preserveNullAndEmpty` is not a valid `$unwind` option — MongoDB raises `OperationFailure: unrecognized option to $unwind stage: preserveNullAndEmpty` (error code 28811). The correct field name is `preserveNullAndEmptyArrays`. | `GET /analytics/departments/summary` and `GET /analytics/leaderboard/late` return 500 Internal Server Error against a real MongoDB instance. Confirmed live on Atlas. | Renamed both occurrences to `preserveNullAndEmptyArrays`. |
| 5 | `tests/test_main.py` — `test_punch_out_no_overtime_under_30_minutes` | The ms constant `1783345920000` is `2026-07-06T13:52:00Z` = 19:22 IST (52 min past shift end), not `13:15 UTC` as the comment claims. The arithmetic `1783312500000 + 33420000` is correct in seconds but the punch-in `1783312500000` is `04:35 UTC`, not `03:58 UTC` as assumed. So the test asserts `overtime_minutes == 0` but the code correctly returns `52`. | Test failed: `AssertionError: 52 != 0`. | Replaced the constant with `1783343700000` = `2026-07-06T13:15:00Z` = 18:45 IST (15 min past shift end → 0 overtime). |
| 6 | `tests/test_main.py` — `test_regularize_422_no_changes` | Test stores `punch_in = epoch_ms_to_datetime(1783312500000)` = 10:05 IST with `late_minutes=0`. When the same ms is re-submitted, `compute_late_minutes` returns 35 (10:05 IST is 35 min late), which differs from the stored 0, so changes are detected and no 422 is raised. | Test failed: `HTTPException not raised`. | Changed stored punch_in to `1783310280000` = 09:28 IST, which is on-time (`late_minutes=0`). Re-submitting the same value genuinely changes nothing, so 422 is correctly raised. |

## Items inspected and decided NOT defects

| Item | Reasoning |
|---|---|
| `compute_late_minutes` uses `elapsed <= timedelta(minutes=10)` for the grace period | Spec says "strictly more than 10:00" is late; `<= 10:00` means on-time. Correct. |
| `attendance_date` subtracts one day for overnight shift when `local.time < shift_end` | Correctly maps a post-midnight punch-in (e.g., 02:00 IST) to the previous day's shift. Verified against sample document #7 (overnight 22:00–06:00). |
| `compute_work_hours` uses `int(elapsed_seconds)` before dividing | Truncates sub-second precision per R1 ("truncated to whole seconds"). Correct. |
| `punch_out` searches with `status $in [PRESENT, WFH, ON_DUTY]` sorted by `punch_in DESC` | ABSENT/LEAVE records have no open punch-in; sorting DESC closes the latest shift first. Correct. |
| Optimistic-lock guard in `regularize_attendance` uses `$expr {$size history} == len` | Ensures no history entry was appended between read and write, making concurrent edits safe (409 for the loser). Correct per spec. |
| `department_trend` fills calendar gaps with a Python loop instead of `$densify` | `$densify` requires MongoDB 6.0+. The Python loop produces identical output. The spec says "such as `$densify`" (suggestion, not mandate). Correct. |
| `serialize_attendance` converts `history[].changes.punch_in/punch_out` from/to to epoch ms | DATA_MODEL.md states these must be epoch milliseconds in the API. Correct. |
